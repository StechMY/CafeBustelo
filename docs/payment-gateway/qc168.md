# QC168 V3 Payment Gateway

## Architecture

Manual deposits keep their existing path: receipt upload, pending review, and a human Filament approve/reject action.

QC168 deposits create a local pending `RechargeRequest` first, call QC168, redirect the customer to the returned payment URL, and wait for a signed server callback. Only a verified `completed` provider state is passed to `RechargeApprovalService::approve`. That existing service remains responsible for the rechargeable wallet ledger transaction, wallet snapshot, accumulated recharge, and first-approved-recharge/Invite Day behavior.

No gateway controller or service directly changes a wallet balance. The browser return page reads local state only.

Withdrawals keep the existing accounting model. Submission reserves the full `WithdrawRequest.amount` by moving it from available balance to locked balance and creates the one withdrawal debit/reservation ledger transaction. Admin approval explicitly selects one of three snapshotted modes: `manual`, `gateway_scheduled`, or `gateway_instant`. Manual approval calls the existing `consumeLocked()` path immediately. Both gateway modes keep the reserve locked and pay `WithdrawRequest.net_amount`; only a verified QC168 `completed` state consumes the full original reserve. None of these completion paths reduces available balance again or creates another debit ledger row.

The QC168 1.40% provider fee is a merchant cost and is not deducted from the user. The application's existing withdrawal fee is already reflected in `net_amount`.

## Environment

```env
QC168_ENABLED=false
QC168_BASE_URL=
QC168_OC_KEY=
QC168_SECRET=
QC168_MERCHANT_UID=
QC168_CURRENCY=vnd
QC168_COUNTRY=vn
QC168_PAYMENT=
QC168_DEPOSIT_PAYMENT=
QC168_WITHDRAW_PAYMENT=vn02
QC168_TIMEOUT=20
QC168_CONNECT_TIMEOUT=10
```

`QC168_PAYMENT` remains a backwards-compatible fallback for both payment settings. Confirm `vn02` and all merchant capabilities with QC168 before enabling either flow.

`QC168_ENABLED` is the environment-only master kill switch. Filament stores only three operational values in the existing `settings` table: `qc168_deposit_enabled` (default `true`), `qc168_withdraw_enabled` (default `false`), and `qc168_withdraw_release_hours` (default `24`, valid range `1..720`). Admin values can never override `QC168_ENABLED=false`. No credential, URL, merchant configuration, payment channel, currency, country, or timeout is stored in the database.

Set production `APP_URL` to the public HTTPS origin. The callback supplied to QC168 is:

```text
${APP_URL}/payment-gateway/qc168/callback
${APP_URL}/payment-gateway/qc168/withdrawal/callback
```

Route generation is proxy-aware through the project's trusted-proxy configuration. Production order creation rejects non-HTTPS base, callback, redirect, and returned payment URLs.

## Signing and callbacks

All request fields are sorted lexicographically and joined as `key=value&key=value`. The signature is lowercase hexadecimal HMAC-SHA256 using `QC168_SECRET`, sent in `OC-Signature`; `QC168_OC_KEY` is sent separately in `OC-Key`.

Callback verification signs every received body field. The provider's misspelled `signture_key` is deliberately preserved and included. Empty strings and zero values are never filtered. Comparison uses `hash_equals`.

Before approval, the callback/sync processor verifies the local merchant order, gateway method/provider, merchant UID, `income` transaction type, configured currency, requested amount at the application's two-decimal precision, optional `recharge` accounting type/payment code, and a documented provider status. `final_amount` is recorded but the approved wallet credit remains the local `RechargeRequest.amount`.

Valid callbacks return HTTP 200 with the plain-text body `success`. Invalid signatures, unknown orders, and mismatched financial fields return non-success responses and never invoke accounting.

## Status and idempotency

`none`, `pending`, `preparing`, and `processing` leave the local request pending. `completed` invokes the shared approval path. `failed`, `reject`, and `overdue` are recorded without credit. `refund` is recorded for review and never debits a wallet automatically.

The processor locks the recharge row in a database transaction. Concurrent callbacks, scheduled reconciliation, and manual sync therefore produce one approval and one ledger credit. Final provider states do not regress; a later refund can be recorded without reversing the existing local approval.

Every callback is saved in `payment_gateway_events`, including invalid signatures, mismatches, duplicates, and processing results. Credentials and authentication headers are not saved.

## Merchant balance indicator

Filament displays the configured QC168 merchant balance beside the SMS balance in the Admin topbar. The read-only lookup posts only `merchant_uid` to `/octopus/api/ledger/get_merchant_ledger` and uses the existing `Qc168Gateway` request signing, authentication headers, and timeouts. It requires only `QC168_BASE_URL`, `QC168_OC_KEY`, `QC168_SECRET`, and `QC168_MERCHANT_UID`; deposit and withdrawal payment channels, country, and bank details are not required for this lookup.

The displayed entry comes from the lowercase `QC168_CURRENCY` response field, defaulting to `vnd`. The provider's exact decimal string is retained in cache and formatted only for display. The topbar shows the configured currency only, not the provider's complete multi-currency ledger or any merchant credentials.

Successful data is cached for five minutes with a 20-second refresh lock. Manual refresh has a global 10-second cooldown. Failed refreshes are retried no more than every 30 seconds and retain the last successful value for up to 24 hours; a failure without a previous value is shown as unavailable, while an explicit provider zero remains a valid zero balance. `QC168_ENABLED=false` displays a disabled state and performs no request.

The Livewire component polls every five minutes, but the cache service decides whether a provider request is needed. A newly completed QC168 deposit or finalized payout marks the balance stale only after its database transaction commits. Duplicate completion events do not invalidate it, and payment events never calculate or mutate the provider balance locally.

## Withdrawal payout lifecycle

Pending withdrawals expose three separately authorized Filament actions in both the table and detail view:

- **Approve Manually** uses no gateway, consumes the existing full locked reserve immediately, stores `approval_mode=manual` and `payout_status=completed`, and creates no payout attempt.
- **Approve & Schedule Gateway Payout** stores `approval_mode=gateway_scheduled`, snapshots the current delay, keeps the reserve locked, and lets the scheduler submit after the exact release time.
- **Approve & Send Gateway Payout Now** commits `approval_mode=gateway_instant`, a zero-hour delay snapshot, and the approved review decision before invoking the same payout dispatch service used by the scheduler. A provider or network failure cannot roll back the approval; the reserve remains locked for retry, sync, cancellation review, or later scheduler recovery.

When the Dashboard automatic-withdrawal setting is off, the environment master switch is off, or required server-side payout configuration is incomplete, only the two gateway approval actions are disabled with an explanation. Backend service methods enforce the same rule. Manual approval and Reject remain available; Reject uses the existing `releaseLocked()` refund path.

For scheduled gateway approval, the local request becomes `approved` with `payout_status=waiting_release`, snapshots the current `qc168_withdraw_release_hours`, and sets `gateway_release_at=reviewed_at + snapshot hours`. Later setting changes never recalculate existing release timestamps. For instant gateway approval, the delay snapshot is `0`, release time equals review time, and dispatch starts only after the approval transaction commits. Both paths create immutable `WithdrawalPayoutAttempt` rows through the same dispatch service. Each attempt has a unique `merchant_order_id` and snapshots the request's bank name, numeric QC168 bank code, account holder, account number, amount, currency, and payment channel. Retry creates a new attempt and never overwrites a previous one.

The outgoing payout fields are fixed as follows:

| QC168 field | Value |
| --- | --- |
| `transaction_type` | `expense` |
| `accounting_type` | `pay` |
| `amount` | `WithdrawRequest.net_amount` |
| `currency` | `vnd` |
| `country` | `vn` |
| `payment` | `vn02` |
| `to` | snapshotted account number |
| `to_name` | snapshotted account holder name |
| `to_bank_name` | snapshotted numeric QC168 bank code, for example Vietcombank `970436` |

`failed`, `reject`, and `overdue` leave the full reserve locked. An authorized admin may retry after a fresh provider inquiry confirms the final failure; the retry uses a new attempt and merchant order ID. Cancellation is allowed after a definitive create failure, a fresh inquiry confirming a safe final failure, or the manual confirmation procedure below, and releases the full reserve once. `processing`, unresolved uncertain submissions, and refunds cannot be cancelled automatically. Refunds are marked for manual review.

For a submission stuck in `create_pending` with `submission_result=uncertain`, the list action menu and withdrawal detail page offer **Manually Confirm Unpaid** to admins with `CancelGateway:Withdrawal` in the withdrawal's support scope. Obtain QC168 confirmation for the exact merchant order ID that it has not paid and will never pay; an instruction to create a new order alone is insufficient. Enter the provider reply and ticket/reference, a reason, and the required acknowledgement. The service locks and rechecks the withdrawal and latest attempt, rejects stale order IDs, and records the admin, time, IP, evidence, reason, and original diagnostic in attempt metadata and an append-only event. No schema migration is needed.

Manual confirmation marks that attempt failed while preserving the original submission metadata and locked reserve. Then choose the existing **Retry Payout** action (requires `RetryGateway:Withdrawal`) to create A2 under the same withdrawal without another debit, or **Cancel Payout and Refund** to release the full requested amount including its fee. These actions can use the recorded manual confirmation without another successful inquiry. A subsequent valid provider state supersedes the manual conclusion; a return to processing blocks retry/refund again, and completion after cancellation follows the existing financial-review path. The evidence remains visible in payout attempt details.

Existing approved withdrawals that were finalized by the legacy approval path remain `payout_status=completed` and are backfilled with `approval_mode=manual`. Existing pre-mode QC168 payout records are classified as `gateway_scheduled`; already-completed records cannot be picked up by the dispatch scheduler. Existing bank names are assigned a numeric QC168 bank code only when the mapping is deterministic; unmapped records keep `bank_code=NULL`, remain eligible for manual approval, and cannot use either automatic payout action.

Withdrawal lifecycle and action records are append-only rows in `payment_gateway_events`, linked to the withdrawal and attempt where known and including actor, source, reason, signature result, and safe payload metadata. Neither `OC-Key` nor the signing secret is persisted.

## Reconciliation and admin access

An accidental **Manual Approval** can be undone using **Undo Manual Payment · Return to Pending** from the withdrawal list or detail page. This requires `ApproveManual:Withdrawal` within the admin's support scope, a reason, and explicit confirmation that no actual transfer occurred and the original payment will not proceed. Only a completed manual approval with a matching `withdrawal.approved_manual` reserve-consumption event is eligible; gateway activity, payout attempts, and cancellation/refund ledgers block the operation. Historical backfilled approvals without this accounting evidence require separate review.

The operation restores the full requested amount to the locked balance, leaves the available balance unchanged, and clears the approval fields so the same withdrawal can be approved again or rejected. The withdrawal row, user, and wallet are locked within one transaction. The original approval event ID prevents duplicate or stale reversals, and `withdrawal.manual_approval_reverted` records the original review, admin, reason, IP, and reserve balances before/after. As with manual reserve consumption, this reserve-only correction is audited in payment gateway events without creating an available-balance credit/debit. The existing immutable approval-mode guard remains enforced outside this explicit reset.

The scheduler runs `qc168:sync-pending-recharges` every five minutes. It queries at most 50 locally pending orders older than two minutes whose previous sync is at least five minutes old, including an inconsistent provider-`completed`/local-pending record that still needs confirmation and approval. Manual execution supports `--limit=1..200`.

It also runs `qc168:dispatch-approved-withdrawals` every minute and `qc168:sync-pending-withdrawals` every five minutes. Dispatch selects only new QC168 withdrawals in `waiting_release` whose exact release timestamp has arrived. Sync reconciles already-created non-final attempts and remains available if the withdrawal feature switch is later turned off, preventing in-flight orders from becoming unobservable.

Filament displays the deposit method, withdrawal approval method, and gateway identifiers/status. Manual approve/reject is hidden for gateway deposits. The Dashboard Payment Gateway Settings action contains only automatic deposit, automatic withdrawal, and withdrawal-delay controls and requires `ManagePaymentGateway:Settings`. The manual deposit sync action requires `SyncGateway:Recharge`. Withdrawal approval modes require `ApproveManual:Withdrawal`, `ApproveScheduledGateway:Withdrawal`, and `ApproveInstantGateway:Withdrawal` respectively. Retry, safe cancellation, and sync require `RetryGateway:Withdrawal`, `CancelGateway:Withdrawal`, and `SyncGateway:Withdrawal`. `Audit:Withdraw` continues to control Reject. The migrations create these permissions but do not grant them to arbitrary roles.

## Deployment

```bash
php artisan migrate --force
php artisan optimize:clear
php artisan schedule:list
php artisan route:list --path=payment-gateway
```

Grant the gateway permissions only to intended admin roles through the existing Shield role UI. No destructive Shield regeneration is required. Confirm the scheduler is running and both public callbacks are reachable over HTTPS. Keep automatic withdrawal off in the Dashboard until payout credentials, `vn02`, numeric bank mappings, callbacks, and a sandbox/provider test payout have all been verified.

After server configuration is verified, set `QC168_ENABLED=true`, run `php artisan optimize:clear`, then enable the desired Deposit/Withdrawal controls in the Dashboard. Gateway approval is blocked while effective withdrawal availability is false; manual approval remains available and finalizes the existing reserve without QC168.

Production acceptance also requires a QC168 test order/callback using the real base URL, merchant credentials, configured `payment` channel, currency, and country. Do not use live customer funds until that provider-side test succeeds.
